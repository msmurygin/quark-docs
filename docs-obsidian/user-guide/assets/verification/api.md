## Product findings

1. **Stub RPCs that look real.** `confirm_shipment` and `create_picking_task` (`services/app-server/src/web/rpcs/wms_task_rpc.rs:10-33`) log "STUB" and return fixed fake JSON. They are in the public catalog with roles ADMIN and MANAGER. A client can believe a shipment was confirmed. Remove them, or mark them clearly. **Fixed (F-07, commit `48086a858`):** both methods were removed from the catalog.
2. **Serial commands drop the numeric error code.** `map_serial_err` (`services/app-server/src/web/rpcs/serial_commands_rpc.rs:37-39`) turns a `SerialError::ValidationFailed` into a text `INVALID_DATA`. The `return_code` (80-95), `class` and `is_overridable` are lost. The receipt path keeps them (`wms-inbound/.../serial_registration.rs:72`). The same code means different wire shapes in two paths. **Fixed (F-14):** the `serial_*` methods answer the RF envelope (`SerialError::into_model_error`) with the code, class and override flag.
3. **Overridable flag with no way to override.** Codes 88 and 91 set `is_overridable: true` (`return_serial.rs:75-82`, `serial_service.rs:257-273`), but no serial code has an override capability (`wms-shared/src/validation_codes.rs:595-610`) and `serial_return` takes no acknowledgement. The "owner policy" described in the enum comment (`validation_codes.rs:472`) is not implemented.
4. **Dead anomaly rules.** `check_two_locations` (89) and `check_velocity` (90) in `libs/wms-serial/src/service/serial_service.rs:529,560` have no caller. Code 93 and the 89 scan only write log warnings (`services/app-server/src/services/cleanup_tasks.rs:1097,1176`). The event `process.serial.flagged_anomaly` has a payload type but nothing in the anomaly path publishes it. **Fixed (P-22):** `serial_ship` runs `check_velocity` and publishes `process.serial.flagged_anomaly`; `check_two_locations` and `check_lot_mismatch` were removed (89 stays a background log scan).
5. **Locked/Disabled users still authenticate.** `UserStatus` is not checked at login or in API key validation (`libs/wms-lib-core/src/model/user.rs:26-33`, `api_key.rs:247`). Only `api_access` blocks keys. A departed employee marked `Disabled` keeps access. The code comment already flags it as a missing gate.
6. **`api_access` flip is delayed up to 30 s** (`api_key.rs:248-258`): no cache invalidation on that change. Revoke does invalidate. Already documented in 02.
7. **Event prefix filter is loose.** `prefix.*` is matched as `starts_with(prefix)` without the dot (`services/app-server/src/services/integration_delivery.rs:440-442`). `process.*` also matches a code like `processfoo`. A pattern such as `process.order.*` matches `process.order_x...` too. Low risk today, but not the documented meaning. **Fixed (F-17):** `prefix.*` takes only the codes under the prefix, at a `.` (`event_code_matches`).
8. **Resolved B1-03: guarded `webhook_url`.** Create/update still store text, but the worker accepts only HTTP(S), refuses redirects, checks every resolved address, and pins the connection to the validated set. Exact tenant/system-scoped private exceptions require `DELIVERY_WEBHOOK_PRIVATE_ALLOWLIST`.
9. **Axum rejections bypass the JSON-RPC envelope.** `rpc_handler` takes `Json(rpc_body)` (`routes_rpc.rs:187`). Invalid JSON, wrong Content-Type or a body over 2 MB gets a plain-text Axum answer (400/415/413/422), not a JSON-RPC error. Clients must handle both shapes. **Fixed (F-16):** `rpc_handler` takes the body as `Result<Json<Value>, JsonRejection>` and answers `RPC_REQUEST_INVALID` in the envelope, keeping the HTTP status (`wms_lib_web::Error::RpcBodyRejected`). `/api/login` still answers plain text.
10. **Orphan event codes.** Eleven seeded codes in `event_registry` are never published (list in 07). A subscriber that filters on them waits for nothing. **Fixed (F-18):** `is_active` now says what is published (enterprise 019: `adjusted`/`moved` on, `reversal` off); `wms-lib-core --test event_catalog_census` keeps the catalog and the code in step.
11. **Generated reference is silent on stubs.** `reference/tasks.md` lists `confirm_shipment` without any hint that it is a stub. The generator (`scripts/docs-api/generate_reference.py`) has no stub marker. Not changed: it needs a source-level marker first.
